R02-T035 — API Verification Notes

Checked: 2026-11-17
README section: ### News (lines 1851–1879)
Method: official documentation review plus direct HTTP header observation.

1. Mediastack

Official docs:
- https://docs.apilayer.com/mediastack/docs/api-documentation
- https://docs.apilayer.com/mediastack/docs/quickstart-guide

Observed documentation:
- Auth is an API access key passed as the `access_key` query parameter.
- The documented endpoint is `https://api.mediastack.com/v1/news`.
- The documentation states that the service supports HTTPS encryption.

Observed request:
  curl -sS -i "https://api.mediastack.com/v1/news?currencies=USD" \
    -H "Origin: https://example.com"

Response:
  HTTP/2 401
  access-control-allow-origin: *
  access-control-allow-methods: GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS
  {"error":{"code":"missing_access_key", ...}}

Interpretation:
- The 401 is caused by the missing API key and does not indicate API unavailability.
- The wildcard CORS header is present on the documented GET response.
- Auth = apiKey, HTTPS = Yes, CORS = Yes.

2. Associated Press

Official docs:
- https://api.ap.org/media/v/docs/Getting_Started_API.htm
- https://developer.ap.org/

Observed documentation:
- "Use HTTPS with TLS 1.2 or 1.3 for all API requests to api.ap.org."
- "An API key is the access key required for making API calls."
- "supply the API key in the x-api-key HTTP request header. The x-apikey header is also currently supported."
- "The AP advises against building browser-based integrations that directly call the AP Media API."
- "the AP is unable to support customers who choose to call Media API directly from a browser."

Observed requests:
  OPTIONS https://api.ap.org/media/v/content/search?q=test
    Origin: https://example.com
    Access-Control-Request-Method: GET

  GET https://api.ap.org/media/v/content/search?q=test
    Origin: https://example.com

Responses:
- OPTIONS: HTTP/2 200 with `access-control-allow-origin: https://example.com`
  and `access-control-allow-methods: *` (gateway-level preflight response).
- GET: HTTP/2 401 with no `access-control-allow-origin` header, because no
  API key was supplied.

Interpretation:
- The 401 is an authentication response, not proof that the API is unavailable.
- Auth = apiKey and HTTPS = Yes are confirmed by official documentation.
- CORS remains Unknown: the preflight is gateway-level, the unauthenticated
  actual response lacks the CORS header, and AP explicitly does not support
  direct browser integrations. No official statement confirms general CORS
  support for authenticated responses.

3. Chronicling America

Official docs:
- https://www.loc.gov/apis/additional-apis/chronicling-america-api/
- https://guides.loc.gov/chronicling-america/additional-features
- https://www.loc.gov/apis/

Observed documentation:
- "Beginning in 2025, the Chronicling America collection is accessible
  exclusively via the loc.gov API."
- "This API is accessible to the public with no API key or authentication
  required, however, rate limiting is enforced."
- The LOC guide directs computational access to the loc.gov API.

Observed requests:
  HEAD/GET http://chroniclingamerica.loc.gov/about/api/
    -> HTTP 308 redirect to https://www.loc.gov/chroniclingamerica/about/api/
  GET https://www.loc.gov/apis/additional-apis/chronicling-america-api/
    -> HTTP 200
  GET https://www.loc.gov/apis/?fo=json
    -> HTTP 200 response headers received
    -> access-control-allow-origin: *
    -> body transfer timed out after 30 seconds; headers were conclusive
  GET https://www.loc.gov/collections/chronicling-america/?fo=json
    -> HTTP 403 Cloudflare challenge in this environment

Interpretation:
- The legacy HTTP documentation URL redirects to HTTPS.
- The official current API is the loc.gov API, which is HTTPS.
- Auth = No is confirmed by the official LOC guide.
- CORS remains Unknown: the actual collection endpoint returned HTTP 403
  without an `access-control-allow-origin` header. The 403 is an inconclusive
  challenge response, not proof that CORS is unsupported. The wildcard header
  on the generic loc.gov API page does not establish CORS for the collection
  endpoint.

No other catalogue values were changed.
